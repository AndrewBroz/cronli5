# The 1.0 public API: design

2026-11-12. Written by the orchestrating model from a conversation with the
maintainer. Not yet approved. Calls the maintainer did not make are marked
**(my call)** and listed again in section 10.

## 1. Intent

cronli5 is at 0.10.0. The renderer rebuild is already a breaking change, so
the next release is 1.0, and 1.0 is the one moment the public API can be
rethought freely. This document says what that API is.

The API is designed for the people who will adopt it, and for the problems
they really have.

**Who they are.** A developer holding a cron string from some scheduler
(crontab, Kubernetes, Quartz, a cloud scheduler) and a locale code from
their application, who wants a description to show to people. Most arrive
from cRonstrue, replacing a call like:

```js
cronstrue.toString('*/5 * * * *', {locale: 'fr', use24HourTimeFormat: true})
```

**What they should find.** cronli5 is the upgrade: clearer sentences, and
at least as much control. Wherever cronli5 offers more power than
cRonstrue (fine-tuning a style, choosing which languages ship, building a
pattern from parts) that power stays.

**What comes after.** cRonstrue's history says ports follow: Python, Java,
Go. The API should make a port a matter of rebuilding from shared
artifacts, not of re-deciding behaviour.

## 2. Principles

1. **Settle what would break later.** 1.0 fixes names and shapes. Anything
   that can be added later without breaking a caller may wait.
2. **Never take away a capability.** 1.0 may rename or regroup. It does not
   remove something a caller can do today. Redundant spellings of one
   capability are not capabilities.
3. **No silent failure.** An option the library cannot honour is an error
   with a message that says what to do, never ignored and never answered
   with a guess. (Today a mistyped field in a custom style does nothing.)
4. **Little for a maintainer to keep up.** This kind of library is rarely
   anyone's first priority. Prefer one table that generates code, tests
   and documentation over three things kept in step by hand.
5. **A portable core, idiomatic edges.** The contract every implementation
   shares is small and made of plain data. Each ecosystem may offer more on
   top. Portability constrains the core, not what JavaScript may offer.

## 3. The portable core

Every implementation, in any programming language, provides this:

```
describe(pattern: string, options: Options) -> string
```

`Options` is a plain record of strings, booleans and one nested plain
record. It can be written in JSON.

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `lang` | string | `"en"` | A language code, optionally with a region: `"uk"`, `"en-GB"` |
| `style` | record | `{}` | Overrides of the language's style table (section 5) |
| `form` | `"fragment"`, `"label"`, `"sentence"` | `"fragment"` | How the description is presented (section 6) |
| `cron` | string | `"standard"` | The flavour of cron the pattern is written in (section 7) |
| `seconds` | boolean | from the flavour | A six-field pattern starts with seconds |
| `years` | boolean | from the flavour | A six-field pattern ends with a year |
| `weekdaysFrom` | `0`, `1` | from the flavour | The number that means Sunday |
| `questionMark` | `"reject"`, `"allow"`, `"require"` | from the flavour | Whether a day field may, or must, be `?` |
| `lenient` | boolean | `false` | Bad pattern input returns the language's fallback text instead of an error |

**The conformance suite.** Each language's paradigm rows are already a
pattern, options and an expected sentence. A script exports them as JSON,
one file per language, and that file is the test a port must pass. This is
why every option is plain data: a row must be able to carry it.

## 4. Languages

**By code.** `lang` takes a code string. This is what adopters hold, what
cRonstrue takes, and what a port needs.

**Region is part of the code.** `"en-GB"` selects British style; `"en"` and
`"en-US"` select the default. The `dialect` option goes away: applications
carry `en-GB`, not a separate dialect setting. A language module declares
which regions it knows and the style each uses.

**Resolution.** An exact match on language and region; otherwise the
language with its default style **(my call)**: `"en-AU"` is described as
`"en"`. A language that is not available is an error (principle 3) that
names the import that would provide it. This is not softened by `lenient`,
which is about pattern input **(my call)**.

**Choosing what ships (JavaScript).** Three ways, none removed:

```js
// 1. As today: import a language and pass it. Only what is imported ships.
import cronli5 from 'cronli5';
import uk from 'cronli5/lang/uk';
cronli5('0 9 * * *', {lang: uk});

// 2. New: build an instance from chosen languages, then use codes.
import {create} from 'cronli5';
import uk from 'cronli5/lang/uk';
import de from 'cronli5/lang/de';
const describe = create({languages: [uk, de]});
describe('0 9 * * *', {lang: 'uk'});

// 3. New: every language, for callers who do not mind the size.
import cronli5 from 'cronli5/all';
cronli5('0 9 * * *', {lang: 'uk'});
```

The default export of `cronli5` is an instance that knows English. There is
no global registration: an instance knows exactly the languages it was
created with.

`create` also accepts defaults for the instance **(my call)**: `options`
for anything but style, and `styles`, a record keyed by language code,
because a style's fields belong to one language. A call's own `style`
overrides fields of its language's default. There is no way to give one
language's style to another, so that cannot fail silently.

```js
const describe = create({
  languages: [en, uk],
  options: {form: 'label'},
  styles: {en: {hour12: false}}
});
```

A module passed as `lang` has no region code to carry. Its regional styles
are reached through the tables it exports (`style: styles.gb`), or by
giving the code to an instance that knows the language (`lang: 'en-GB'`).

**Which languages are in 1.0.** Only languages rebuilt through the renderer
process exist in the tree; the earlier ones were removed and are not
carried forward. Every language that ships meets this whole contract. The
questionnaire therefore gains questions for the things this document
makes each language answer: how a label is capitalised, its 12- and
24-hour forms and which is its default, its short names, and its regions.
The every-language entry point holds whatever exists at release; the
`fr`, `de` and `pt-BR` in this document's examples are illustrations.

## 5. Style

A style is a language's table of copy-editor choices: the words for a.m.
and noon, the range word, the serial comma, day-first dates. It never
changes the order of a sentence.

* `style` is a record that overrides fields of the table the language and
  region select. Each language defines its own fields.
* **24-hour time and short names move into the style**, as `hour12`
  (boolean) and `short` (boolean). Whether a house writes `17:30` is the
  same kind of choice as `a.m.` against `am`, and a region can then carry
  its own default. The top-level `ampm` and `short` options go away.
* **Named styles are exported as plain tables**, so a caller can pass one
  or spread and adjust it. This keeps `house`, which has no region, and is
  finer control than a name:

  ```js
  import {styles} from 'cronli5/lang/en';
  cronli5('0 9 * * *', {style: {...styles.house, hour12: false}});
  ```

* **An unknown field, or a value of the wrong type, is an error**
  (principle 3). Today both are silently ignored.

## 6. Form

One option, three values:

| `form` | Example | For |
| --- | --- | --- |
| `"fragment"` (default) | at 9 a.m. every day | embedding in a sentence |
| `"label"` | At 9 a.m. every day | a standalone label in an interface |
| `"sentence"` | Runs at 9 a.m. every day. | a complete sentence, as the CLI prints |

`"label"` is new. It is how most cRonstrue output is shown, and cronli5 had
nothing between a lowercase fragment and a full sentence. Each language
owns how its label is capitalised.

`form` replaces the boolean `sentence` option. The `cronli5.sentence()` and
`cronli5.fragment()` methods are removed: they are a second and third
spelling of one option (principle 2), and a function with methods does not
port.

## 7. How the pattern is read

A caller knows where a pattern came from, not which flags that implies. So
`cron` names a flavour, and the flavour sets the reading flags. A flag
given explicitly overrides the flavour.

| Flavour | `seconds` | `years` | `weekdaysFrom` | `questionMark` |
| --- | --- | --- | --- | --- |
| `"standard"` | by field count, as today | as today | 0 | `"reject"` |
| `"quartz"` | as today's `quartz: true` | as today | 1 | `"allow"` |

Two flavours ship in 1.0, the two already implemented. **A further flavour
is added only after its semantics are checked against that scheduler's own
documentation.** The boolean `quartz` option becomes `cron: "quartz"`.

`weekdaysFrom` and `questionMark` are today's `quartz` option taken apart
into the two things it bundles, so each can be set alone.

* `weekdaysFrom: 1` means exactly what Quartz numbering means today, under
  any flavour: 1 is Sunday through 7 for Saturday, 0 is an error, and the
  numbering applies inside the weekday operators (`6L`, `2#2`) and to the
  bare `L` alias. With `weekdaysFrom: 0`, 0 and 7 are both Sunday, as now.
* `questionMark: "allow"` reads `?` as "no specific value", the same as
  `*`, in either day field, without requiring it. The Quartz flavour
  selects it (settled with the maintainer, 2026-11-12): 0.10's `quartz`
  option accepts a pattern with no `?`, and requiring one would take that
  away. `"require"` (exactly one day field is `?`) is available as a flag
  for a caller who wants Quartz's own strictness. The adapter uses
  `"allow"` too, because cRonstrue accepts `?` under any settings. `"standard"` keeps rejecting `?`,
  because under our own API a `?` is the sign of a Quartz pattern whose
  weekday numbers would otherwise be misread without a word.

**Pattern input (JavaScript).** The string, array and object forms all
stay. Building a pattern from parts without assembling a string is
something cRonstrue cannot do. Only the string form is part of the
portable core.

## 8. Deliberately not in 1.0

All of these can be added later without breaking a caller.

* **Time zones.** The need is real: the server runs in UTC and the reader
  does not. A plain hour offset is risky: a fire that crosses midnight
  moves to another day, and a fixed offset is wrong for part of the year
  wherever clocks change. The safe first step, when it comes, is naming
  the zone ("at 9 a.m. UTC every day"); conversion would be done in the
  core on the sets of values, refusing what cannot be said.
* **"Both day fields must match."** Classic cron fires when either the day
  of the month or the weekday matches. Some schedulers can require both
  (croner's `domAndDow` option, default off, and a `+` prefix per
  expression). It would be a reading flag, and it gives schedules people
  want: "on Fridays that fall on the 13th". The option waits, but **the
  questionnaire gains its question now** (how does this language say a
  weekday that falls on a date?), because adding a question after ten
  languages exist costs ten times as much.
* **A verbose mode.** It is the opposite of what the descriptions aim at.

## 9. The cRonstrue adapter

A separate entry point, `cronli5/cronstrue`, for a nearly mechanical swap:

```js
import cronstrue from 'cronli5/cronstrue';
cronstrue.toString('*/5 * * * *', {locale: 'fr', use24HourTimeFormat: true});
```

It translates the call and adds no behaviour. It cannot reproduce
cRonstrue's wording and does not try: people switch because the wording is
different.

| cRonstrue option | Becomes | Notes |
| --- | --- | --- |
| `locale` | `lang` | `pt_BR` becomes `pt-BR`. A language cronli5 lacks is an error; cRonstrue answers in English. |
| `use24HourTimeFormat: true` | `style: {hour12: false}` | |
| `throwExceptionOnParseError: false` | `lenient: true` | cronli5 returns its fallback text, not the parser's message |
| `dayOfWeekStartIndexZero: false` | `weekdaysFrom: 1` | |
| (always) | `questionMark: "allow"` | cRonstrue reads `?` as `*` whatever its options; the caller's numbering is explicit in the row above |
| `trimHoursLeadingZero` | accepted | cronli5's 12-hour times never have a leading zero; with 24-hour time, `true` is an error **(my call)** |
| `verbose: true` | error | |
| `monthStartIndexZero: true` | error | |
| `logicalAndDayFields: true` | error, until section 8's flag exists | |
| `tzOffset` other than 0 | error | |

The result uses `form: "label"`, the closest to cRonstrue's capitalised
text. The adapter is built on the every-language entry point.

**One table is the source** (principle 4): it generates the adapter's
mapping, its tests, and the option table in
`docs/migrating-from-cronstrue.md`.

## 10. Calls made in this document

For the maintainer to check while reading:

* A region cronli5 does not know falls back to its language's default
  style; a language it does not have is an error, even in lenient mode.
* The style fields are named `hour12` and `short`.
* The third form is named `"label"`.
* The new reading flags are named `weekdaysFrom` and `questionMark`, and
  the flavours `"standard"` and `"quartz"`.
* Instance defaults split into `options` and per-language `styles`.
* The adapter rejects `trimHoursLeadingZero: true` with 24-hour time
  rather than ignoring it.
* The removed convenience methods are not kept as deprecated aliases.

## 11. Moving from 0.10

| 0.10 | 1.0 |
| --- | --- |
| `dialect: 'gb'` | `lang: 'en-GB'` |
| `dialect: 'house'` | `style: styles.house` |
| `dialect: {…}` | `style: {…}` |
| `ampm: false` | `style: {hour12: false}` |
| `short: true` | `style: {short: true}` |
| `sentence: true`, `cronli5.sentence(p)` | `form: 'sentence'` |
| `cronli5.fragment(p)` | `cronli5(p)` |
| `quartz: true` | `cron: 'quartz'` |
| `lang: module` | unchanged |
| `seconds`, `years`, `lenient` | unchanged |
| array and object patterns | unchanged |

The CLI's flags follow the same renames.

## 12. Checked, and not yet checked

Checked on 2026-11-12:

* croner: the option is `domAndDow`, default `false` (either field
  matches); a `+` prefix on the weekday field requires both. From its
  README.
* Quartz: "Support for specifying both a day-of-week and a day-of-month
  value is not complete (you must currently use the '?' character in one
  of these fields)." From its CronTrigger tutorial.
* cRonstrue 3.14.0, as installed here: `tzOffset` passed to `toString`
  changed nothing in four trials, including one that should have crossed
  midnight. Its `toString` signature does not list the option.

Not settled:

* Whether Spring's `CronExpression` requires both day fields to match. Its
  Javadoc and reference page do not say. This matters only when a
  `"spring"` flavour is proposed.
* How many callers use the array and object pattern forms and the
  convenience methods. The first are kept regardless; the second are
  removed on principle, and the package's dependents would show the cost.

## 13. Left to the builder

* How the types express that `style` depends on `lang`.
* The names of error classes, and whether option errors share a class with
  pattern errors.
* How a language module declares its regions and exports its styles.
* The script that exports paradigm rows as the conformance suite, and
  where the files live.
* The form of the adapter's source table.
* Order of work, and whether this lands before or after the Ukrainian
  rebuild. Nothing here depends on a second language existing, but
  section 4's instance and section 5's regions are easiest to prove with
  two.
